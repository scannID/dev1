# 1000 TPS readiness runbook

Prove Scanny can sustain ~1000 mixed TPS across ~1000 restaurants (menu/QR scans, orders, payments).

## Pass / fail gates

| Gate | Target |
| --- | --- |
| Sustained throughput | ~1000 TPS for 15–30 minutes |
| Error rate | &lt; 0.1% (`scanny_errors` / `http_req_failed`) |
| p99 menu / scan / order (app-side) | &lt; 200 ms |
| DB CPU | &lt; 70% during the run |
| Replica kill | Stop one of `api-1` / `api-2` / `api-3`; traffic continues; recover when restarted |

## Prerequisites

1. Production-shaped stack with **3 API replicas**, Postgres, Redis, and Keycloak on its **own** DB (`keycloak`):

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build
```

2. Seed or generate **1000 business IDs** and at least one catalog item per business (IDs must match what you pass via `BUSINESSES` / seed script). For a dry run against empty IDs, the k6 script still exercises the API (404/400 count as handled responses for capacity, not product success).

3. For load tests, run the API with the `loadtest` profile (or set `RATE_LIMIT_ENABLED=false`) so per-IP rate limits are not the first wall:

```text
SPRING_PROFILES_ACTIVE=prod,loadtest
```

4. Install [k6](https://k6.io/docs/get-started/installation/).

## Run the mix

From the repo root:

```bash
# Short smoke (2 minutes @ 1000 TPS)
k6 run -e BASE_URL=https://api.scanny.app -e TPS=1000 -e DURATION=2m -e BUSINESSES=1000 loadtests/scanny-1000tps.js

# Full gate (15 minutes)
k6 run -e BASE_URL=https://api.scanny.app -e TPS=1000 -e DURATION=15m -e BUSINESSES=1000 -e VUS=400 -e MAX_VUS=1000 loadtests/scanny-1000tps.js
```

Local API (single process) for a smaller proof:

```bash
k6 run -e BASE_URL=http://localhost:4000 -e TPS=100 -e DURATION=1m -e BUSINESSES=50 loadtests/scanny-1000tps.js
```

### Traffic mix

| Share | Call |
| ---: | --- |
| ~40% | `GET /api/businesses/{id}/menu` |
| ~25% | `POST /api/businesses/{id}/scans` |
| ~20% | `POST /api/businesses/{id}/orders` |
| ~10% | `POST /api/payments/initiate` + status |
| ~5% | `GET /api/payments/providers` |

## Replica kill test

While the 15m run is in progress:

```bash
docker stop scanny-api-2
# observe k6 error rate stays under gate; Caddy health removes the instance
docker start scanny-api-2
```

Confirm Redis pub/sub and rate limits still behave (no duplicate storm; limits still enforced when enabled).

## What to watch

- API: CPU, heap, Hikari active connections (`HIKARI_MAX_POOL_SIZE`, default 20 per replica)
- Postgres: CPU, connections (Compose baseline `max_connections=200`), slow queries on `orders` / `qr_scan_events`
- Redis: memory, command latency (menu cache, rate limits, scan dedupe, WS fan-out)
- Outbox lag: `outbox_events` rows with `processed_at IS NULL` should clear within a few seconds
- Caddy upstream health on `api-1` / `api-2` / `api-3`

## Architecture notes (already in tree)

- Three API containers behind Caddy round-robin ([`docker-compose.prod.yml`](../../docker-compose.prod.yml), [`deploy/Caddyfile`](../../deploy/Caddyfile))
- Keycloak DB separated via [`deploy/postgres/01-keycloak-db.sql`](../../deploy/postgres/01-keycloak-db.sql)
- Hot-path indexes + outbox table: Flyway `V20__tps_readiness_indexes_outbox.sql`
- Menu Redis cache, slim order create, Redis QR dedupe, async outbox for WS/audit/receipt/paid cascade
- Stub payment webhooks: `POST /api/payments/webhooks/stub` with `{"paymentId":"PAY-...","status":"Paid"}`

## Failure playbook

| Symptom | Likely cause | Action |
| --- | --- | --- |
| Instant 429s | Rate limits still on | Enable `loadtest` profile or raise `RATE_LIMIT_*` |
| p99 &gt; 200 ms on menu | Cache miss / Redis down | Verify `scanny.redis.enabled=true` and Redis health |
| Outbox backlog grows | Dispatcher stuck / DB lock | Check API logs for `Outbox event … failed`; scale API or fix payload |
| Connection exhaustion | Pool × replicas &gt; Postgres | Lower `HIKARI_MAX_POOL_SIZE` or raise `max_connections` |
| Spike after replica kill | Slow health removal | Tune Caddy `health_interval` / `health_timeout` |
